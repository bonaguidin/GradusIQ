## 🔴 Blocking / real students affected

- [ ] **GAP's synchronous execution risks exceeding Vercel's function timeout for real students.** Re-verified 2026-08-24, no change since last audit (2026-08-17). The full chain (`api.py:analyze_gap` → `_run_protected_feature` → `GapRunner.run` → `role_requirements_for` → `role_research_agent.get_role_requirements` → `CareerFeatureRunner.run`'s DeepSeek R1 synthesis call) is entirely synchronous. Two costs stack: (1) the DeepSeek R1 call itself, documented as routinely 100–200s+ (`ai/openrouter_client.py:16-20`), timeout set to 300s to accommodate it; (2) `role_requirements_for` (`gap.py:188-201`) loops over uncovered target roles **sequentially**, each bounded by a 90s wall-clock budget (`role_research_agent.py:115`). `frontend/vercel.json` caps `api/proxy.mjs` at `maxDuration: 300` — one uncovered role plus the DeepSeek call can already approach or exceed that ceiling.

  This is a **hard blocker for extending auto-run analysis to real student accounts**. `useCachedAnalysisRun` (`frontend/src/hooks/useCachedAnalysisRun.ts:26-49`) already deliberately withholds auto-run for real students because of this — they only get GAP via a manual click, which still hits this same unbounded path.

  Three fix directions, none implemented:
  - **(a) Decouple into a background job, client polls/receives an event.** Correct long-term fix; no queue/worker infra exists today. `student_analysis_cache` (`api.py:1005-1025`) could grow a status column, but this is a real infra lift.
  - **(b) More aggressive cross-student role-research caching.** Partially moot: `role_research_cache.json` is already shared/global, keyed by role name only, no TTL. Doesn't touch the dominant DeepSeek cost.
  - **(c) Raise the Vercel timeout ceiling.** Cheapest if the plan supports it (unverified — needs checking in the Vercel dashboard, not assumed); even 800s isn't a full fix for a student with multiple uncovered roles.

  **Next step:** (a) is the real fix — scope the background-job/status-column design. (c) is worth a 5-minute check of the actual Vercel plan tier before ruling it out as a stopgap.

### Freeform / manual-review requirement groups — three structural gaps

- [ ] **TAMU Core Curriculum (and similar freeform, `requires_manual_definition` groups) can never resolve to SATISFIED regardless of completed coursework** — `evaluate_requirement_tree()` short-circuits these to `MANUAL_REVIEW` unconditionally. Root cause: no course-list/category data exists anywhere in the catalog for TAMU's Core Curriculum sub-categories (creative arts, social/behavioral sciences, American history, government, etc.) — a data gap, not a logic gap. Fix needs (a) ingesting a category taxonomy per course (`ucc_attributes` exists sparsely on some TAMU catalog entries but isn't a complete master list), and (b) wiring `course_records.catalog_course_id` into requirement evaluation (column exists, unused today). SMU's manual groups (Technical Electives, Advanced Major Electives) are a different case — inherently adviser-judgment-gated by the source requirement's own design, not a data gap, and probably shouldn't auto-resolve even once data exists.

- [ ] **No way to distinguish "manual review because data is missing" from "manual review because it's inherently an adviser judgment call."** Needs a `manual_review_reason` field set at catalog-ingestion time (by a human reviewing each source requirement), not inferred from existing fields (`notes_html` null-ness is the closest signal but is a guess, not a classification).

- [ ] **No way to determine whether a requirement group belongs to a term the student has already completed.** TAMU's "Year — Season" naming is a plan-sequence position, not a calendar term, and there's no logic anywhere mapping plan position to actual enrolled term. Fragile even if built (breaks under gap semesters, AP credit shifts, summer terms) and institution-naming-dependent (SMU's manual groups carry no term reference at all). A softened-copy-only fix shipped instead of attempting this (see PR for the "We can't automatically verify..." copy change).

## 🟡 Syllabus grade calculator — review redesign + category-weight editing shipped, several residual gaps

The 2026-08-29→30 redesign (PRs #61–#67) reclassified curve/late-work/makeup rules as non-blocking and moved them to a passive "Professor's Rules" sidebar, gave cutoff-overlap conflicts a real propose/confirm flow with a manual-threshold-editor fallback, added syllabus removal via soft delete (live in production), removed dead UI (assessment-count display, "Ignore this rule" button), and filtered the now-moot `unknown_assessment_count` finding out of the review list. A follow-on pass (PRs #79–#81, #86, 2026-09-06) closed the `category_weight_validation` confirm dead end with an editable category-weight breakdown and made What-If scores take precedence over an entered score. See "Shipped." Remaining:

- [ ] **`_check_grade_thresholds` never flags an overlap that involves a single-bound threshold.** `GradusIQ_career/syllabus/reconciliation.py` — the overlap scan runs only over `bounded = [t for t in thresholds if t.minimum is not None and t.maximum is not None]`, so a threshold expressed as one bound only (`"A: 90+"`, `"F: below 60"` → `maximum` set, `minimum` None) is excluded entirely. A syllabus like `A: 90+` / `B: 85–92` genuinely overlaps at 90–92 but produces no `overlapping_grade_thresholds` finding.
